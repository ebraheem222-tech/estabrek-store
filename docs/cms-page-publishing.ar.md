# نشر صفحات CMS

هذه المرحلة تصلح دورة نشر الصفحات الحالية. تحرير وظائف Shop وCart والجداول المخصصة وتحويل الصور إلى مسارات SVG مراحل لاحقة في [الخطة الشاملة](superpowers/specs/2026-11-07-cms-platform-control-design.ar.md).

الحالة: نُشرت المرحلة على `main` بالإصدار `556ead4`. تحقق الفحص الفعلي من لوحة Cloudflare والسيرفر على Railway والمتجرين على Vercel. لا يشمل هذا إكمال المراحل اللاحقة أو إعادة نشر صفحات التاجر تلقائيًا.

## استخدام المحرّر

- زر «نشر» ينقل محتوى المسودة ويضبط الصفحة الجديدة على `PUBLISHED`، مع حفظ مراجعة سابقة في العملية نفسها.
- المواعيد السابقة تبقى افتراضيًا. إذا كانت هناك نافذة نشر، يمكن اختيار «انشر الآن وألغِ مواعيد البداية والنهاية» صراحةً. الصفحة المؤرشفة تحتاج اختيار إعادة نشرها.
- شريط الحالة يميّز المسودة والمنشورة والمجدولة والمنتهية والمؤرشفة، ويفصل حفظ النشر عن وصول طلب تحديث كاش الواجهة.
- «افحص الرابط العام» يقرأ الرابط من المواقع المضبوطة على السيرفر. «الصفحة ظاهرة» تعني أن الفحص وجد الصفحة ومعرّف النشر المتتبّع إن وجد؛ ليست مقارنة لجميع المحتويات أو للأجزاء المشتركة. تغيير لغة المعاينة يستلزم فحص تلك اللغة مجددًا.
- «أعد تحديث الموقع» يعيد محاولة إبطال الكاش فقط. لا ينشر مسودة ولا يغيّر حالة صفحة خاصة. النشر وإعادة المحاولة يتطلبان صلاحية `pages:publish`.

رابط صفحة غير موجودة يعيد HTTP404 من مسار CMS قبل بدء بث المحتوى. اختبار المتصفح يزور الرابط قبل نشر الصفحة، ثم ينشرها ويتأكد من ظهور المحتوى وزخارف SVG نفسها بالعربية والإنجليزية. لم تُنشر صفحة التاجر `/t` تلقائيًا ضمن الاختبار.

## التعارضات والاستمرارية

محتوى الصفحة وحالتها ونافذتها والمراجعة السابقة وسجل توصيل الكاش تُحفظ داخل معاملة واحدة. تُقفل صفوف الصفحة والأقسام وترجماتها قبل قراءة لقطة النشر، حتى لا يتداخل تعديل من المحرّر القديم بين فحص التعارض وحفظ المحتوى. تغير الحالة أو الرابط أو المواعيد أو مراجعة المسودة يتطلب مراجعة جديدة؛ «فرض النشر» يعالج اختلاف المحتوى فقط. المسودات القديمة التي لا تحتوي لقطة حالة تبقى مقروءة.

سجل التوصيل محفوظ في `Page.publicationDelivery` وليس في ذاكرة السيرفر فقط. مهمة `cmsPublish` تفحص المحاولات المستحقة كل30 ثانية، بحد50 صفحة في الدفعة وست محاولات لكل سجل، وتأخير متزايد من30 ثانية حتى30 دقيقة. تُجدول إعادة التحقق عند بداية نافذة النشر ونهايتها أيضًا. انقطاع الواجهة بعد حفظ المحتوى لا يحوّل نجاح الحفظ إلى خطأ500. عمليات الإقرار وإعادة المحاولة مشروطة بالإصدار السابق حتى لا تستبدل نشرًا أحدث.

## إعداد النسخة المستقلة

تستخدم النسخة عنوان إعادة التحقق المفرد الموجود `STOREFRONT_REVALIDATE_URL`. يمكن إضافة `STOREFRONT_REVALIDATE_URLS` كقائمة عناوين مفصولة بفواصل، حتى8 وجهات. مثال توضيحي فقط:

```env
STOREFRONT_REVALIDATE_URL=https://shop.example.com/api/revalidate
STOREFRONT_REVALIDATE_URLS=https://second-shop.example.com/api/revalidate
```

يجب تطابق سر إعادة التحقق الموجود في إعدادات Backend وStorefront، وضبط `STOREFRONT_URL` على المتجر المقصود. لا يلزم تغيير عنوان الصفحة أو محتواها. عدم تهيئة الوجهات يظهر في شريط الحالة. إضافة دعم الوجهات لا تعني أن كل متجر منشور قد أضيف إلى بيئة الاستضافة تلقائيًا.

فحص الرابط لا يقبل مضيفًا يرسله المتصفح؛ يستخدم الوجهات المضبوطة فقط، بلا اتباع تحويلات، وبمهلة وحجم استجابة محدودين. سجلات التوصيل لا تخزن السر أو نص استجابة الموقع.

## قاعدة البيانات والتحقق

الترحيل الجديد `20261107110000_page_publication_delivery` يضيف عمودJSONB قابلًا للقيمة الفارغة فقط. لا يحذف بيانات ولا ينشر صفحات قائمة. اختبارات قاعدة البيانات تستخدم PostgreSQL معزولًا في GitHub Actions باسم `estabrek_cms_publish_test`، ولا تستخدم قاعدة التاجر.

هناك مشكلة سابقة منفصلة عند إعادة تشغيل **كل تاريخ الترحيلات على قاعدة فارغة**: بعض تاريخ `SiteSettings.checkoutMode` يضيف العمود بعد وجوده في الترحيل الأول. لم تُعدّل ترحيلات مطبّقة سابقًا أو بصماتها. اختبار هذه المرحلة يبني مخطط ما قبل الإضافة على قاعدة الاختبار المعزولة، ثم يطبّق ملف الترحيل الجديد الفعلي. إصلاح مسار التثبيت من الصفر ما زال مطلوبًا قبل اعتماد معالج تسليم نسخ جديدة للعملاء.

مقاييس القبول: اختبارات سياسة النشر والتعارضات وصلاحيات HTTP وتراجع المعاملة وجدولة إبطال الكاش، اختبارات PostgreSQL الحقيقية، اختبارات المحرّر، ومتصفح محلي مع واجهة Next الفعلية. بيانات المتصفح ورفع الملفات محلية تجريبية. فحص الموقع المنشور يقتصر على القراءة.
