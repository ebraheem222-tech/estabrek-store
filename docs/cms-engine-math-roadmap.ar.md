# خارطة تطوير رياضيات محرك محرر CMS

**الهدف:** جعل السحب والتحجيم والمحاذاة داخل محرر المتاجر قابلة للتوقع عبر الحاويات المتداخلة والشاشات المختلفة، ثم توسيع التحويلات الهندسية تدريجياً دون التضحية بسرعة التفاعل.

**حالة الوثيقة:** اقتراح للمراجعة، مبني على قراءة الكود في 6 نوفمبر 2026. كل ما تصفه المراحل التالية قدرة مستقبلية ما لم يُذكر صراحة أنه موجود الآن. هذه الوثيقة خطة فقط؛ تنفيذ الميزات والحزم ومخطط البيانات يأتي بعد اختيار المرحلة المناسبة. إصلاح تحديث المعاينة الحالي مسار منفصل، ولا توجد وعود بمواعيد إنجاز.

**النهج المقترح:** تطوير المحرك النقي الموجود مع إبقاء المتصفح مسؤولاً عن تخطيط HTML والنصوص. لا نستبدل CSS بمحرك فيزياء شامل. يبدأ العمل بعقد إحداثيات صحيح ودقيق، ثم حركات مقيدة ومحاذاة، ثم قيود تخطيط خطية محلية؛ تبقى الهندسة الإسقاطية ثلاثية الأبعاد مرحلة لاحقة مستقلة.

## 2. فصل الإصلاح الفوري عن المشروع الهندسي

إصلاح إعادة تحميل iframe غير الضرورية عند كل حفظ مسار فوري منفصل. معيار نجاحه أن يستمر الإطار نفسه أثناء الحفظ المعتاد مع بقاء scroll والتحديد، وأن تصل المعاينة الصحيحة. لا يحتاج هذا الإصلاح solver ولا مصفوفات 4×4، ولا ينبغي تأجيله حتى اكتمال هذه الخارطة.

بقاء iframe لا يجعل القياس الحالي أدق تلقائياً؛ تحديث البيانات، إعادة render، إعادة حساب layout، وإعادة تحميل document أحداث مختلفة. المراحل الهندسية أدناه تعالج دقة التفاعل وكلفة تحديثه بعد تثبيت مسار الحفظ.

## 3. عقد الإحداثيات قبل أي خوارزمية جديدة

تُسمّى المساحات صراحة في الحسابات والاختبارات، وتستخدم الأرقام العشرية الكاملة داخل المحرك. التقريب للنص أو الحفظ الحدّي يكون في نهاية العملية، لا بين التحويلات.

| الرمز | المساحة والوحدة | المرجع |
| --- | --- | --- |
| `Lᵢ` | إحداثيات border-box المحلية للعنصر، CSS px قبل transform | الأصل أعلى يسار صندوق العنصر؛ padding/content لهما إزاحة معروفة مستقلة |
| `H` | إحداثيات padding-box للحاوية التي يتم الوضع فيها، CSS px | ليست بالضرورة border-box الأب في الشجرة؛ تراعي containing block وwrappers وscroll المحلي |
| `D` | إحداثيات document داخل iframe، CSS px | scroll الصفحة مضاف مرة واحدة؛ لا تُضاف scroll الحاويات مرة ثانية إذا كانت سلسلة التحويل تتضمنها |
| `V` | viewport داخل iframe، CSS px | `pV = pD − scrollIframe` للحالة المحورية البسيطة |
| `C` | مساحة canvas/overlay في الإدارة، CSS px | الأصل بالنسبة إلى عنصر الـcanvas؛ pan وzoom يحددان ظهور iframe فيها |
| `A` | client coordinates لنافذة الإدارة، CSS px | موضع المؤشر؛ يُطرح موضع الـcanvas قبل الحساب، ولا يُطرح pan مرتين |
| `B` | بكسلات bitmap الفعلية عند الحاجة للرسم | `pB = devicePixelRatio × pC`؛ DPR لا يدخل حساب pointer أو layout |

في المسار الحالي المحوري، العلاقة المرجعية هي:

```text
pC = pan + zoom × (pD − scrollIframe)
pD = scrollIframe + (pC − pan) / zoom
```

هذه العلاقة لا تستبدل مصفوفة transforms الخاصة بأسلاف العنصر داخل iframe. Pan/zoom الإدارة، scroll الصفحة، scroll الحاويات الداخلية، transform-origin، وحافة/padding الحاوية معاملات مختلفة.

يقترح اعتماد متجهات عمودية وترتيب ضرب واحد معلن. تمثيل `Affine=[a,b,c,d,e,f]` الموجود يطابق:

```text
       [ a c e ]
M2D =  [ b d f ]       p′ = M2D × [x y 1]ᵀ
       [ 0 0 1 ]

Mlocal = T(layoutOffset) × T(origin) × F(transformList) × T(−origin)
M(Lᵢ→D) = M(parent→D) × M(Lᵢ→parent)
M(Lᵢ→C) = T(pan) × S(zoom) × T(−scrollIframe) × M(Lᵢ→D)
pLocal = inverse(M(Lᵢ→C)) × pCanvas
```

`F` هو ترتيب تحويلات CSS الفعلي، بما يشمل الخصائص المنفردة إذا استُخدمت؛ لا تُخلط `rotateZ` المعلنة مع matrix computed فيتكرر الدوران. تُضمّن إزاحات wrappers والـcontaining block وscroll الداخلي وفق مسار DOM. قراءة `computedStyle.transform` وحدها لا تعطي مصفوفة local→document كاملة. المراجع المعيارية لترتيب التحويلات وواجهات النقاط والمصفوفات: [W3C CSS Transforms](https://www.w3.org/TR/css-transforms-2/#ctm)، [W3C Geometry Interfaces](https://www.w3.org/TR/geometry-1/#dommatrix).

النقاط تستخدم `w=1`، ومتجهات الإزاحة affine تستخدم `w=0`. في الإسقاط perspective لا تتحول إزاحة كبيرة بمصفوفة خطية واحدة؛ تُحوّل نقطتا البداية والنهاية أو يُستخدم Jacobian محلي لخطوة صغيرة فقط. إذا كانت المصفوفة singular أو شديدة السوء عددياً، يعاد قرار «غير قابل للتحرير المباشر» مع الاحتفاظ بالقيمة السابقة؛ لا تُمرر NaN ولا تُستخرج scale من AABB كبديل.

## 4. تعريف أنماط الحركة المقترح

هذه أوضاع سلوك للحركة داخل المحرر، مستلهمة من فكرة تقييد المحاور، وليست ادعاء تطابق مع نظام Android. اختيار افتراضي مقترح للمراجعة: المحور يتبع مساحة الحاوية `H`، ولذلك يظهر مائلاً على الشاشة إذا دارت الحاوية. RTL يغيّر معنى start/end في anchors، ولا يعكس المحور الرياضي `x` بصمت.

| الوضع | قيد الحركة المقترح | علاقة العنصر بالحاوية |
| --- | --- | --- |
| رأسي فقط `vertical` | `ΔxH = 0` | التحرك على `yH` داخل حدود الأب المؤهلة؛ يبقى العرض/الحجم مستقلين عن قيد الحركة |
| أفقي فقط `horizontal` | `ΔyH = 0` | التحرك على `xH` داخل حدود الأب المؤهلة |
| المحوران `both` | `ΔxH, ΔyH` مسموحان | يبقى العنصر محصوراً في الحاوية الحالية؛ لا يعاد إسناد الأب بمجرد المرور فوق حاوية أخرى |
| حر `free` | المحوران مسموحان | يمكن تجاوز حدود الأب المرئية والانتقال لحاوية أخرى مؤهلة عند الإفلات؛ تستمر قواعد الأقفال والعمق ومنع الدورات |

**تمييز `both` و`free` هنا تفسير مقترح يحتاج تأكيداً لاحقاً من صاحب المنتج:** الأول bounded داخل الأب والثاني يسمح بالانتقال بين الآباء. لا نفرض هذا التفسير على البيانات الحالية، ولا نعيد تسمية `CanvasMode: free|flow` تلقائياً؛ `flow` الحالي مسؤول عن ترتيب العناصر ضمن التخطيط، وهو مفهوم مستقل.

رياضيّاً، تبدأ الحركة بطلب مؤشر غير مقيد `dC`. إذا كان `A` الجزء الخطي من `H→C` وكان اتجاه الحركة المحلي المسموح `v`، فإن `u=A×v` هو اتجاهه على الشاشة. أقرب حركة مسموحة إلى المؤشر بمسافة الشاشة هي:

```text
t = dot(dC, u) / dot(u, u)
dH = t × v                dC_allowed = A × dH
vertical:   v = (0, 1)
horizontal: v = (1, 0)
both/free:  dH = inverse(A) × dC
```

مع skew أو scale غير موحد، تحويل `dC` إلى local ثم تصفير مركّبة يعطي إسقاطاً مائلاً، وقد لا يكون أقرب موضع للمؤشر على الشاشة؛ المعادلة أعلاه تحسم اختيار «أقرب شاشة». ويمكن تعميمها على أساس مسموح `Q`: تقليل `‖A Q t − dC‖²`. عكس الاتجاه أو قفل Shift لا يتغلب على قيد دائم؛ تكون الحركة ناتج تقاطع القيود. إذا كان التقاطع نقطة فالناتج صفر. تُحل الحدود وsnapping داخل فضاء الحركة المسموح، فلا يصلح snapping أن يعيد تحريك المحور المقفول.

## 5. الأدوات الرياضية المطلوبة وحدود كل أداة

### 5.1 تحديد الإصابة والتصادم

يبقى AABB مناسباً كـ**broad phase**: query في الشبكة الحالية للحصول على مرشحين قريبين من المؤشر أو المسار swept. بعدها يعمل **narrow phase** على الإطار والشكل الحقيقيين:

1. تحويل المؤشر إلى local لاختبار مستطيل/دائرة/مسار، أو اختباره داخل quad مُسقط إذا كان هذا هو الشكل المرئي. لا يُحدد عنصر من فراغ زوايا AABB حول عنصر مدور.
2. احترام تقاطع منطقة العنصر مع clip/overflow لجميع الأسلاف. ترتيب الرسم والـstacking context وتحديد العنصر المرئي أو الأب القابل للتحرير سياسات معلنة؛ العمق في شجرة CMS وحده لا يساوي ترتيب الرسم في المتصفح.
3. الاستمرار بـSAT للأجزاء المحدبة. للأشكال المقعرة: اختبار مسار دقيق للاختيار، ثم تفكيك محدب محدود ومخزن للتصادم إن احتاج المنتج ذلك؛ convex hull الحالي يبقى تقريباً معلناً. قواعد holes وfill-rule يجب أن تكون متطابقة مع الرسم.
4. عند الحاجة إلى منع عبور عائق رفيع، استخدام swept tests/وقت أول اصطدام للأشكال المدعومة أو خطوات تكيفية بحد خطأ مثبت. الوضع الحالي ذو خطوات محدودة لا يُسوّق كـcontinuous collision detection.
5. تحديث خلايا العناصر المتغيرة فقط. لا نستبدل الشبكة بشجرة مكانية أعقد إلا إذا أظهر benchmark أن تباين أحجام العناصر يجعل الشبكة مكلفة.

تُختبر النقاط على الحدود بصورة متسقة: هل اللمس إصابة؟ هل اللمس تصادم يمنع الحركة؟ سياسة الاختيار يمكن أن تقبل الحد بينما التصادم لا يعده اختراقاً. سماحية المستخدم بوحدة screen CSS px مستقلة عن دقة predicate العددية. لا يصلح epsilon ثابت واحد لكل من zoom والأطوال واختبار اتجاه ثلاثة نقاط. يمكن اعتماد orientation predicate تكيفي للحالات شبه المتراصفة التي تثبت حاجتها؛ [مرجع Shewchuk الأصلي حول robust predicates](https://www.cs.cmu.edu/~quake/robust.html) يشرح مشكلة إشارة المحدد قرب الصفر والحساب التكيفي.

### 5.2 التحجيم مع طرف أو pivot ثابت

يكون الحجم المحلي المقاس مصدر الحقيقة، لا AABB المرسوم. إذا كانت الزاوية المقابلة في local هي `a`، وتحويلها عند بدء السحب هو `q0=M0×a`، يجب أن يبقى موضعها المرئي ثابتاً بعد تغيير الحجم. عند ثبات الجزء الخطي `A` أثناء resize:

```text
q0 = t0 + A × a0
tNew = q0 − A × aNew
```

`aNew` هو إحداثي **نفس الطرف الدلالي** بعد تغير الأبعاد. عند origin نسبي للعرض/الارتفاع يعاد حساب origin والتحويل؛ لا يكفي حفظ center القديم. في سحب edge، يثبت الخط المقابل وتثبت نقطة مرجعية معلنة عليه لمنع انزلاق غير مطلوب على امتداده. في سحب corner تثبت الزاوية المقابلة. في التحجيم حول pivot اختاره المستخدم تثبت تلك النقطة بدلاً منهما.

مع ratio ثابت `r=w0/h0`، القيد `w−r×h=0` خطي ما دام `r` ثابتاً. تُطبّق min/max ثم يعاد حساب الموضع من الطرف الثابت؛ clamp للحجم وحده قد يزيح الطرف. يتم التفريق بين تغيير `width/height` الذي يعيد تدفق المحتوى وبين تكبير محتوى حاوية بـscale، كما يفعل خيار scale contents الحالي. تبقى الأبعاد غير سالبة، ولا يسمح لعبور المقبض للطرف المقابل بإحداث reflection ضمني قبل قرار منتج صريح.

### 5.3 snapping كاختيار مستقر تحت قيود صلبة

المسار المقترح يجمع مرشحي الحواف والمراكز والفجوات والشبكة، ثم يختار مجموعة صغيرة قابلة للتحقيق. يمكن صياغة اختيار المرشح `k` والحركة `d` كالتالي:

```text
min J(d,k) = α × ‖projectToScreen(d) − dPointer‖²
           + βk × residualAlignment(d,k)²
           + λ × switchPenalty(k, previousCandidate)
subject to: axis lock, parent containment, locked nodes, size limits
```

هذه دالة هدف مقترحة لا يعني عرضها أن solver الموجود يحسبها الآن أو أن Cassowary يحل هدفاً تربيعياً. في البداية تكفي مقارنة مرشحين محليين وحل إزاحة 1D/2D صغير؛ solver القيود لاحقاً يمكن أن يستخدم أخطاء خطية مع ترتيب قوى.

المسافات والعتبات تقاس على الشاشة حتى يبقى الإحساس ثابتاً مع zoom. قيم بدء للتجربة فقط: التقاط عند 6 CSS px وفك عند 10 CSS px؛ المرشح الحالي يحتفظ بهويته حتى يتجاوز عتبة الفك أو يفوز بديل بفارق واضح. هذا hysteresis خاص بالمحاذاة، منفصل عن `HoverFilter` الحالي. tie-break ثابت بمعرّف الدليل ونوعه، فتغيير ترتيب مصفوفة المرشحين لا يسبب اهتزازاً. يعرض الدليل فقط إذا بقي residual ضمن السماحية **بعد** الحدود والتصادم. Ctrl/Cmd يزيل تفضيلات snapping، ويستمر احترام القيود الصلبة.

### 5.4 تخطيط بقيود خطية محلية

أول نطاق مفيد هو حاوية واحدة ومجموعة مترابطة من الأبناء، وليس حل كل صفحة المتجر عند كل pointermove. المتغيرات `x,y,w,h` تُعرّف في مساحة الحاوية قبل التحويل. أمثلة:

```text
x ≥ paddingStart                         y ≥ paddingTop
x + w ≤ parentWidth − paddingEnd         y + h ≤ parentHeight − paddingBottom
w ≥ minWidth                             h ≥ minHeight
xA + wA + gap = xB                        yA + hA/2 = yB + hB/2
w − ratio × h = 0                         // ratio ثابت فقط
```

`required` للحدود التي يؤكد المنتج صلابتها، وللمحور المقفول والحدود الدنيا. قيود strong/medium/weak لتفضيل المؤشر والمحاذاة والمحافظة على الوضع السابق. ترتيب القوى جزء من التصميم ويُثبت في الاختبارات؛ لا يكفي اختيار أوزان ضخمة عشوائياً. اقتراح البداية: required يتغلب على كل تفضيل؛ strong لسحب المستخدم؛ medium للمحاذاة المؤقتة؛ weak للـstay. يمكن ترجيح المحاذاة داخل فئة strong بقرار تفاعل واضح، بدلاً من أن تختار المكتبة السلوك بالصدفة.

يُقيّم solver خطي تزايدي من عائلة Cassowary بمثال محدود قبل اختيار أي dependency. تُضاف القيود البنيوية مرة، وتتغير edit suggestions أثناء السحب؛ لا يعاد بناء النظام كله لكل حدث. [ورقة Cassowary الأصلية](https://constraints.cs.washington.edu/solvers/cassowary-tochi.pdf) تشرح المعادلات والمتباينات الخطية والحل التزايدي، و[توثيق Kiwi الرسمي](https://kiwisolver.readthedocs.io/en/latest/basis/basic_systems.html) يوضح required/soft strengths وedit variables. يستخدم Kiwi قوى عددية بدلاً من hierarchy رمزية، ولا يقدم stay constraints الأصلية مباشرة؛ [توثيقه الداخلي](https://kiwisolver.readthedocs.io/en/latest/basis/solver_internals.html#creating-strengths-and-their-internal-representation) يشرح هذه الفروق. يُختبر أن تراكم القيود الضعيفة لا يقلب الأولويات المعتمدة، وتُحاكى stay بمعادلات ناعمة أو suggestions عند اختيار تطبيق يحتاج ذلك.

الأب الأصغر من min-size ابنه قد يجعل القيود الصلبة متناقضة. يُرفض القيد الجديد أو الحركة المؤدية للتناقض مع حفظ آخر حل صالح وشرح السبب في المحرر؛ لا يُخفّض required بصمت ولا يُصغّر محتوى التاجر دون طلب. حدود «صندوق التخطيط» و«الزوايا المرئية بعد الدوران» تختلف؛ containment المرئي داخل أب محدب يمكن التعبير عنه بنصاف مستويات عندما يكون الدوران/scale ثابتين أثناء الخطوة.

الدوران المتغير، `sin/cos`، منظور 3D، استجابة النص للعرض، التفاف grid، والاختيار بين «يسار العائق أو يمينه» ليست جميعها قيوداً خطية مستمرة. تبقى في طبقات منفصلة: قياس المتصفح للمحتوى، اختيار حالة/discrete candidate، وحساب تحويلات. تجميد angle يجعل بعض المعاملات خطية؛ لا يجعل حل الدوران نفسه خطياً. لا نقحم collision non-overlap العام في solver خطي على أنه أربع متباينات متزامنة، لأن الفصل المطلوب اختيار بين بدائل.

## 6. وراثة responsive وحفظ القصد

السلوك الحالي في `effectiveLook` يدمج base ثم tablet ثم mobile. تبنى المراحل الجديدة على هذا الترتيب، مع تتبع مصدر كل قيمة في الحسابات: موروثة أم override في الشاشة النشطة. تعديل mobile لا ينسخ القيم الفعالة كلها إلى mobile، وإزالة override تعيد الوراثة. تغيير base ينتقل إلى الشاشات التابعة فقط حيث لا يوجد override للخاصية نفسها.

يُحفظ قصد التخطيط عند الإمكان: start/end أو نسبة أو اتصال بحافة، وليس عينة screen pixels مأخوذة من zoom الإدارة. القياس intrinsic مثل ارتفاع النص ناتج للمتصفح وليس override جديداً بمجرد السحب. بداية drag تلتقط snapshot للشاشة والقياسات؛ إذا تغير breakpoint أو الخط أو حجم الحاوية أثناءها، تعاد مواءمة آمنة إلى قياس حديث أو تلغى الحركة بوضوح، ولا تجمع مصفوفتين من إصدارين مختلفين.

أوضاع الحركة المستقبلية وقوى القيود تحتاج قرار نطاق وراثة قبل التنفيذ: هل هي إعداد شاشة، أم سلوك عنصر، أم تفضيل مؤقت للمحرر؟ هذه الوثيقة لا تضيف حقول تخزين. يبدأ إثبات الفكرة داخل الحالة المؤقتة، ويؤجل تصميم الاستمرار إلى موافقة مستقلة على سلوك المنتج.

## 7. تحديث تزايدي بإصدارات وdirty sets

لا يكفي بقاء iframe لتحسين الأداء إن أعيد قياس الصفحة وفهرستها كلها. يقترح تقسيم أسباب الاتساخ داخلياً إلى: محتوى/حجم intrinsic، layout، transform، clip، paint/overlay، وبنية الشجرة. لكل snapshot هندسي ارتباط واضح بإصدار المشهد، والشاشة، والقياس، وجلسة السحب؛ لا تستخدم نتيجة متأخرة لهندسة مشهد أحدث. هذه مفاهيم داخلية مقترحة، وليست تعديلاً منفذاً لبروتوكول الرسائل.

- تغير transform لأب يوسّخ world transforms لأحفاده وbounds/fهرستهم؛ لا يوجب إعادة قياس النص كله.
- تغير عرض أو نص قد يعيد تدفق إخوة وآباء، فيُوسّع نطاق القياس حسب تبعية التخطيط؛ الاقتصار على العقدة المكتوبة وحدها غير صحيح.
- scroll الصفحة في المشاهد العادية يغير `D→C` فقط؛ sticky/fixed وحركات scroll والقص المحلي قد تحتاج تحديث عناصرها أيضاً، فلا نعمم هذه القاعدة دون تصنيفها.
- pan/zoom الإدارة يحدّث mapping والـoverlay والفهرس بحسب مساحة تخزينه. يمكن حفظ فهرس مستقر في `D` وتحويل query إليه لاحقاً إذا أثبت القياس كلفة فهرس `C` الحالي؛ لا نغيّر هذه المساحة جزئياً دون عقد موحد.
- تقرأ DOM measurements في دفعة واحدة قبل الكتابة، ثم تجرى الحسابات النقية، ثم writes/overlay في دفعة. يدمج rAF أحداث المؤشر ويستخدم أحدث طلب؛ يبقى commit/history واحداً عند الإفلات، وتستعيد Escape/pointercancel المعاينة الأصلية.
- أثناء معاينة السحب، تُميز كتابات المحرر المؤقتة عن تغييرات DOM الخارجية حتى لا تنشأ حلقة MutationObserver→قياس→كتابة→MutationObserver. المقارنة بإصدار ومصدر معروفين أدق من تجاهل كل mutation لعدد ثابت من المللي ثانية.

عند تأجيل مهمة مكلفة أو نقلها خارج thread العرض، تصل نتيجتها برقم snapshot وتُرمى إن تقادمت. البدء بـWorker أو WebGL ليس شرطاً؛ يحدده قياس لاحق يثبت أن حساباً نقياً محدداً يتجاوز الميزانية وأن كلفة النسخ لا تلتهم الفائدة.

## 8. المرحلة المتأخرة: عناصر مستوية مع إسقاط ثلاثي الأبعاد

دعم authored rotateX/rotateY أو أب مدور لا ينتج من تدوير AABB. الخطوة الأولى هي frame affine كامل؛ بعدها فقط يُختبر نموذج projective لعناصر DOM المستوية. هذا لا يعد بمحرر مجسمات أو meshes ثلاثية الأبعاد.

التمثيل المقترح متجه `[x,y,z,1]ᵀ` ومصفوفة 4×4 كاملة متوافقة مع ترتيب CSS. إذا كانت المصفوفة المتراكمة من local إلى الشاشة الإسقاطية `N`:

```text
[X Y Z W]ᵀ = N × [x y z 1]ᵀ
screenX = X/W                 screenY = Y/W
```

لا يُجرى قسمة perspective قبل اكتمال الجزء المناسب من سلسلة التحويل. يجب احترام `perspective-origin` و`transform-origin` و`transform-style: flat/preserve-3d` وعمليات clipping/flattening وترتيب الرسم. سلسلة CSS عامة قد تتضمن flattening يفقد عمقاً، فلا يوجد دائماً inverse واحد مفيد لكل الشجرة. [نموذج التحويلات والتسطيح في W3C](https://www.w3.org/TR/css-transforms-2/#3d-rendering) هو المرجع؛ نجاح أربع زوايا في fixture بسيط لا يثبت دعم كل حالات CSS.

لتحويل المؤشر إلى عنصر مستوٍ، يوجد مساران دقيقان في نطاقهما:

**شعاع مع مستوى:** في سياق 3D قابل للعكس، تختار نقطتان عند عمقين معلومين مختلفين في مساحة الإسقاط نفسها، وتعكس مصفوفة العرض/الإسقاط وتحولهما بعد القسمة بـw إلى `r0,r1` في فضاء مشترك. عندئذ `d=r1−r0` والشعاع `r(t)=r0+t d`. للمستوى ذي النقطة `q` والعمودي `n`:

```text
t = dot(n, q − r0) / dot(n, d)
hit = r0 + t × d
pLocal = inverse(Mlocal→world) × hit
```

يُرفض الشعاع شبه الموازي للمستوى، والتقاطع خلف اتجاه الرؤية، والنقاط المقطوعة وفق سياق العرض. تُحوّل normals بعكس transpose عند nonuniform scale؛ تحويل normal كأنه نقطة خطأ. لا نضع `screenZ=0` عشوائياً ثم نعكس مصفوفة وندعي استرجاع النقطة المحلية.

**Homography للمستوى المحلي `z=0`:** إذا توفر إسقاط صحيح لذلك المستوى ولا يعبر منطقة غير قابلة للرؤية، تختزل العلاقة إلى مصفوفة 3×3:

```text
    [ N11 N12 N14 ]
H = [ N21 N22 N24 ]
    [ N41 N42 N44 ]

[u v w]ᵀ = inverse(H) × [screenX screenY 1]ᵀ
localX = u/w                localY = v/w
```

هذا inverse إسقاط مستوٍ، وليس عكس AABB. تُثبت قابلية بناء `H` الصحيحة من سياق DOM المدعوم؛ وجود `DOMMatrix` أو quad وحده لا يحل stacking والقص. تُرفض المصفوفات/المستويات المنهارة و`w` القريب من الصفر، وتُطبق معالجة الرؤية قرب المستوى الكاشف بدلاً من مد bounds إلى اللانهاية.

في reparent affine يمكن الحفاظ على الإطار العالمي مبدئياً بواسطة:

```text
MlocalNew = inverse(MparentNew→world) × MlocalOld→world
```

لكن الناتج قد يحتوي skew أو reflection لا يمكن تمثيله بخواص العنصر الحالية، أو يتجاوز حدود scale/translation. لا يُسقط الناتج بصمت على rotate+uniform-scale؛ ترفض الحاوية غير القابلة للتمثيل أو تعرض سياسة تحويل مستقلة معتمدة لاحقاً. في perspective/flattening لا تُعمم معادلة reparent هذه قبل إثبات أن كلا السياقين يسمحان بالتمثيل والحفاظ على الشكل المقصود.

## 10. ميزانيات أداء مستهدفة، وليست نتائج مقاسة

يُنشأ benchmark قابل للتكرار يوثق الجهاز والمتصفح وحجم viewport وDPR وzoom وحالة الطاقة والبناء وحرارة cache. fixture البداية المقترح: 2,000 عقدة مقاسة، نحو 400 مرئية، عمق يصل إلى الحد الحالي 12، مع مجموعات transform وscroll ونصوص؛ مجموعات ضغط إضافية 5,000 و10,000 عقدة لتحديد منحنى التدهور، لا لوعد تشغيلها بالسرعة نفسها.

| القياس في السيناريو المرجعي | الهدف الابتدائي للمراجعة |
| --- | --- |
| رياضيات pointer query + constraints بعد الحصول على القياسات | `p95 ≤ 3 ms` على جهاز المكتب المرجعي؛ يسجل عدد المرشحين، ولا يُفترض أنه دائماً أقل من 100 |
| دورة التفاعل كاملة على شاشة 60 Hz | البقاء داخل `16.7 ms` غالباً؛ `p95 input→overlay ≤ 33 ms` هدف منفصل يقاس فعلياً |
| جهاز محمول مرجعي أضعف | هدف تفاعل `30 fps` مع `p95 input→overlay ≤ 67 ms`؛ يراجع بعد baseline |
| دفعة قراءة هندسة حتى 100 عنصر dirty مرئي | `p95 ≤ 6 ms` هدف؛ الحالات التي تسبب reflow واسعاً تقاس منفصلة |
| الفهرسة والتحديث | تحديث عنصر واحد لا يعيد بناء كل المشهد؛ توثيق تكلفة أول قياس منفصلة عن السحب المستمر |
| مهام طويلة أثناء drag | لا مهمة ذاتية للمحرك تتجاوز `50 ms` في fixtures المقبولة؛ القياسات الكاملة تقطع أو تؤجل دون قبول geometry قديمة |

إذا تعارض الهدف مع الدقة، يُقلّل نطاق المرشحين أو معدل القياس أو كثافة الزينة، ويستمر عرض آخر حل صالح؛ لا يصبح تقريب AABB الخاطئ «وضعاً سريعاً» للتحرير الدقيق. تحدد baseline الأرقام النهائية قبل استخدامها كبوابات إصدار.

### خصائص مولّدة على الرياضيات النقية

- **عكس وتركيب:** لمصفوفات finite جيدة التكييف، `inverse(M)×(M×p) ≈ p` و`compose(A,B)` يساوي تطبيق B ثم A. تشمل سلاسل origins وtranslation وrotation وscale غير موحد، مع tolerance نسبي للحجم والتكييف، لا رقم ثابت أعمى.
- **رفض الانهيار:** scale صفر أو قريب من الصفر، مصفوفة nonfinite أو projective `w≈0` لا ينتج عنها patch/موضع NaN؛ الحالات شبه المنهارة لها نتيجة رفض محددة.
- **المحاور:** مركبة الحركة المحظورة تساوي صفراً ضمن tolerance؛ النتيجة أقرب نقطة شاشة على الاتجاه المسموح؛ snapping والتصادم لا يفكان القفل.
- **resize:** موضع الزاوية/الطرف الثابت قبل وبعد متساوٍ؛ نسبة الأبعاد محفوظة؛ min/max لا يسببان drift؛ origin أعلى/وسط/أسفل وorigin عام في التطوير الجديد. الحجم المحلي يبقى معروفاً عند 44.9° و45° و45.1°، ولا يستخرج بعكس معادلة AABB غير القابلة للتحديد.
- **الاختيار:** narrow phase لا يختار خارج الشكل أو داخل hole/clip مخفي؛ تغيير ترتيب المرشحين لا يغير tie-break؛ broad phase لا يستبعد إصابة يقرها narrow phase.
- **التصادم:** وجود overlap متناظر؛ اتجاه الإزاحة الفاصلة صحيح عند تبديل الجسمين؛ التماس وحده لا يصبح اختراقاً؛ الجسم داخل جسم، الحواف المتوازية، الرؤوس المكررة، والأشكال شديدة النحافة لا تكسر الحساب.
- **القيود:** تكرار نفس edit suggestion ثابت؛ إعادة حل النظام بلا تغيير لا تحرك العناصر؛ required متحقق أو تعارض معلن؛ تكديس قيود weak لا ينسخ أولوية strong وفق السياسة المعتمدة.
- **reparent:** الإطار العالمي محفوظ ضمن الخطأ العددي إذا كان الناتج قابلاً للتمثيل؛ النقل المعاكس يعيد الحالة الأصلية دون تراكم rounding؛ إذا لم يكن قابلاً للتمثيل يرفض بدلاً من تشويه الصورة.
- **responsive والإصدارات:** تبديل ترتيب وصول قياسات قديمة وحديثة لا يقبل القديمة؛ إزالة mobile override تعيد القيمة الموروثة؛ تعديل base لا يمحو tablet/mobile overrides.

لا تحتاج هذه الخصائص إلى حزمة جديدة لبدء الإثبات: يمكن توليد عينات seeded داخل أدوات الاختبار القائمة؛ يقيّم إطار property-based مخصص لاحقاً إن كان shrink/replay مفيداً بما يكفي.

### قبول داخل متصفح حقيقي

| الحالة | الدليل المطلوب |
| --- | --- |
| zoom من 0.1 إلى 4، pan، scroll صفحة وحاويات متداخلة، DPR مختلف | المؤشر والمقابض والحدود تتطابق؛ لا تضاعف للـscroll أو DPR؛ انحراف نقطة مرجعية مدعومة لا يتجاوز `0.5 CSS px` على الشاشة في الحالات جيدة التكييف |
| دوران العنصر وأب مدور، scale غير موحد وorigin متغير | المقابض تتبع الزوايا الحقيقية؛ resize يحفظ الطرف المقابل؛ المناطق التي تقع داخل AABB وخارج quad لا تختار العنصر |
| RTL وLTR؛ mouse وtouch/pen وkeyboard | دلالات start/end صحيحة؛ قفل المحور موحد؛ pointer capture/cancel وEscape يعيدان الحالة؛ gesture التمرير المعتادة لا تتحول إلى سحب غير مقصود |
| أوضاع الحركة الأربعة | vertical/horizontal لا drift؛ both يبقى داخل الأب؛ free يعبر ويعرض الحاوية المؤهلة ويحافظ على الشكل عند الإفلات؛ أقفال/دورة/عمق تمنع النقل غير المشروع |
| intrinsic text وauto/% layouts؛ تحميل خط/صورة أثناء التفاعل | لا تجميد أبعاد موروثة دون قصد؛ تحديث قياس أو إلغاء آمن؛ لا استعمال snapshot مختلط |
| snapping عند حدود متقاربة وعائق يقطع المحاذاة | لا تبديل متكرر للمرشح قرب العتبة؛ hysteresis موثق؛ لا خط محاذاة كاذب بعد تطبيق الحدود |
| حفظ، undo/redo، إعادة إسناد أب، ثم إلغاء drag | كل حركة مكتملة خطوة تاريخ واحدة؛ الإلغاء لا يكتب؛ حفظ عادي يبقي iframe والـscroll؛ المعاينة المؤقتة تنظف ولا تتسرب إلى شاشة أخرى |
| 3D لاحقاً: منظور وأب preserve-3d/flat، مستوى شبه edge-on، قص وخلفية | مقارنة screen↔local مرجعية؛ ray-plane/H تعطي نفس النقطة في النطاق المشترك؛ الحالات غير القابلة للعكس/المخفية ترفض بأمان دون تقريب AABB |

يُسجل الخطأ العددي بالأرقام بجانب screenshots؛ الصورة وحدها لا تثبت ثبات pivot. وتشغّل suites المشتركة في fixture بالتسلسل إذا كانت تشترك في draft واحد، وفق harness القائم.

## 12. القرارات التي تبقى للمراجعة قبل تنفيذ مراحلها

1. اعتماد معنى `both` المقيد داخل الأب و`free` العابر للحاويات، أو تعديل هذا الفرق.
2. اعتماد المحاور المحلية للحاوية بدلاً من محاور الشاشة؛ المقترح الحالي محلي مع أقرب إسقاط مرئي.
3. تحديد أولوية المؤشر وsnapping داخل التفضيلات الناعمة، ومعنى حدود الأب عندما يكون الابن أكبر منها.
4. تحديد نطاق وراثة أوضاع الحركة والقيود، وسياسة تحويل/رفض reparent الذي ينتج skew أو reflection غير قابل للحفظ حالياً.
5. تحديد مجموعة CSS/3D التي يُعلن دعمها بعد الاختبارات، ثم اختيار ميزانيات الأجهزة المرجعية من القياس.

يمكن تنفيذ المراحل الأولى دون حسم محرر 3D أو اعتماد solver عام. القيمة المباشرة هي مسار حفظ مستقر، عقد إحداثيات موحد، ثم تحريك وتحجيم صحيحان يمكن إثباتهما؛ الرياضيات الأكثر تعقيداً تأتي عند وجود سلوك منتج واضح واختبار يبررها.
